Q Ecosystem

A personal, local-first lab that ties together the machines I have access to (a laptop, an older Intel Mac, my university's compute pool, a backup drive, and free cloud tiers) so I can build and run coding projects without paying for infrastructure.

Node map

Problem

I wanted to explore coding projects in simulation, data analysis, monitoring and AI tooling, but did not have the compute or budget for dedicated servers or cloud services. I did have access to scattered resources: my laptop, an old Mac, my school's engineering compute network, and the free tiers that cloud providers offer. The problem was turning those into one usable system rather than a pile of separate machines.

What I did

Designed and built Q: a collection of small, independent projects that share one set of machines and one set of rules. I defined each machine's role, connected them, and built a visualizer so I can see what every node is doing at a glance.

How

  • Main (M3 Max MacBook Pro, 36 GB): interactive development, architecture, and review. It is not an autonomous host.
  • Brain (older Intel Mac, 16 GiB): the always-available execution machine, reached over a private Tailscale network. It runs deterministic Python services and local Ollama models, and only uses a language model where reasoning is actually needed.
  • ECC (SCU Engineering Computing Center, a pool of Linux machines): reached only through a gate script that I wrote. The gate runs detached, rule-checked jobs on my university account and enforces limits of 2 jobs, 4 cores, and 16 GiB.
  • Backup: a 2 TB USB drive attached to Brain, tracked as a storage node.
  • Dispatch: a software router on Brain that decides which node gets each task. Free cloud nodes (Oracle, Google Cloud, Lightning AI, Kaggle, Colab) are registered but disabled until I approve them, and every one is reached through Brain, never directly.
  • Architecture rules: Python first, local models only where needed, no continuous cloud-API dependence, and strict isolation between projects. Integration between projects is deliberate, never automatic.
  • Visualizer: a read-only node-telemetry map driven by a JSON registry of nodes and links, with live probes, job lists, and storage state.

Results

  • A working multi-machine system with one registry, one map, and clear rules, running on hardware and free resources I already had.
  • Seventeen registered projects: 1 live, 2 working, 4 scaffold with code, and 10 dormant. Examples include a swarm and maritime simulator, local network anomaly detection, and a multi-model decision council.
  • The university pool has run 206 jobs to completion through the gate (18 failed), including analysis jobs for my senior design project.
  • Compute and storage costs are zero, with an architecture that can add nodes by registering them rather than rebuilding.
